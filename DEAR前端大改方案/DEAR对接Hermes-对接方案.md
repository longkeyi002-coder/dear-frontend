# DEAR 对接 Hermes · 对接方案（BFF 架构）

> 适用对象：负责把 Hermes 能力接进 DEAR 的实现 AI  
> 范围：**全套照搬 Hermes dashboard 的功能**（聊天 / 技能 / MCP / 系统控制台 / 记忆画像 / 看板 / 子代理 / cron / 平台连接器），用 DEAR 自己的壳（移动端优先 + 用户审美）重新呈现。  
> 本文只定「**对接方案**」（架构 + 连接 + 能力映射 + 实施分期），不写实现代码。  
> 配套：本目录另两份《整体前端适配 Hermes-框架规格.md》《UI与动线设计规格书.md》是 UI/动线切片；本文是「DEAR 后端 ↔ Hermes」的通路层。

---

## 0. 给龙龙读的执行摘要（大白话）

- **一句话**：DEAR 自己的前端「壳」不动大方向，但在它后面加一个**翻译官**（把 `backend.py` 升级成 BFF）。这个翻译官去跟 Hermes 说话，把 Hermes 的全部能力搬进你的驾驶舱。
- **你不用重造 Hermes 的逻辑**——Hermes 负责聪明地干活，DEAR 只负责「借能力 + 用你喜欢的样子呈现」。
- **隐私底线**：你的 Hermes 账号 token 只存在 DEAR 后端，**绝不进前端、绝不进手机、绝不写死 IP**。
- **为什么需要中间这层翻译官**：① token 不外泄；② 把 Hermes 的原始数据翻成 DEAR 前端好懂的格式；③ DEAR 的壳本身能离线跑，只「拉数据」时才联网；④ 统一报错和重试。

## 2. 连接与认证（最关键的一环）

### 2.1 Hermes 暴露的接口面（已核实）

- **OpenAI 兼容代理**（`hermes proxy`）：把 Hermes 能力包装成标准 Chat Completions，**这是 DEAR 对话接入的最顺路径**；支持流式（SSE）。
- **Web API**：`hermes_cli/web_server.py` 约 19905 行、**130+ 路由**、**6 个 WebSocket**；前端 `lib/api.ts` 自动注入 session token 与 `?profile=`。
- **端口 9119**，默认绑 `127.0.0.1`。**非回环或配了 `public_url` 就强制开 auth gate，无 auth provider 会拒绝启动（fail closed）**；`--insecure` 已失效。

### 2.2 认证方式

- Hermes web 用 **session token**（随 `?profile=` 注入）。DEAR BFF 持有用户的 Hermes token。
- token **由用户在 DEAR 设置里录入** → 存 DEAR 后端、加密落盘 → **绝不进前端、绝不进手机、绝不写死 IP**（替换之前硬编码的 `43.108.101.95`）。
- ⚠️ 因为 Hermes 非回环强制 auth gate（fail closed），**DEAR 必须带合法 token，否则整条通路被拒**。这是对接的第一道坎，必须先打通。

### 2.3 网络通路

- Hermes 在阿里云，DEAR 后端经反向隧道 / 服务端地址可达。
- DEAR 设置项只需两项：**Hermes 基地址** + **token**；地址从设置读取，不留硬编码。

## 4. BFF（backend.py）职责与模块

1. **配置模块**：Hermes `base_url` + `token`（加密存储、设置录入、可一键清空；键名脱敏）。
2. **代理层**：`/api/chat` → 转发 Hermes OpenAI 代理，SSE 透传；网络/鉴权/限流错误**显式返回 + 可重试**（替换现有的静默 fallback）。
3. **翻译层（adapter）**：每个能力一个 adapter，把 Hermes 原始 JSON → DEAR 前端友好 schema；新增能力只加 adapter，不动前端结构。
4. **缓存**：模型/技能等相对静态的列表缓存，降低请求与 token 消耗。
5. **安全**：secrets（One-Token Secrets）**绝不向前端下发明文**；token 仅后端使用。
6. **离线**：DEAR 壳本身 100% 离线可跑；仅「拉数据/对话」需联网。
7. **错误契约**：统一错误态 + 重试入口，不把「演示已停用」当兜底。

## 6. 实施分期（虽全套照搬，交付仍分阶段，避免一次巨改失控）

| 期      | 内容                            | 说明                           |
| ------ | ----------------------------- | ---------------------------- |
| **P0** | BFF 骨架 + 认证 + 聊天经 OpenAI 代理打通 | 先让「能连、能聊、带 token 不被拒」成立      |
| **P1** | 技能 / MCP / 系统控制台 接入           | 最像「驾驶舱」的三块，优先                |
| **P2** | 记忆/画像 / 看板 / 子代理 / cron / 连接器 | 剩余能力，按依赖顺序接                  |
| 每期     | 保证离线壳可跑、不引入新依赖（第三方库本地打包）      | 与既有清理清单（硬编码 IP/演示残留/死代码）一并收口 |

## 7. 编码前必核实清单（避免编造接口）

1. Hermes **OpenAI 兼容代理**的确切 base path 与鉴权头（header 名/格式）。
2. `web_server.py` 各能力的**路由路径**：skills / mcp / memory / system / cron / subagents / kanban / connectors。
3. **6 个 WebSocket** 各自用途与消息格式（哪些用于流式、哪些用于状态推送）。
4. token **获取/刷新**方式：session token 还是 API key？有无过期与刷新机制？
5. 自托管 Hermes 的**推荐暴露方式**：反向隧道 vs 公网 + auth；非回环强制 auth gate 下的 DEAR 接入姿势。
6. kanban 在后端是否真有数据支撑（官方前端疑似死代码），决定 DEAR 是否实接还是先占位。

---

## 8. 风险与注意

- **auth gate fail closed**：Hermes 非回环强制鉴权，DEAR 必须正确持 token，否则整条通路拒绝——P0 必须先验证。
- **不重造 Hermes 逻辑**：BFF 只翻译/呈现，复杂智能仍在 Hermes 侧；DEAR 是壳与自有业务层。
- **隐私**：token / 密钥只在后端；前端只拿「翻译后、脱敏后」的数据。
- **离线优先**：壳离线可跑是底线，联网只用于拉数据与对话。
- **分步验证**：每接一个能力，先用真实 Hermes 接口跑通再进前端，不要一次巨改后整体联调。
