## Hermes 前端代码审查（用户催进度后自己接手完成）

**产出**：`Hermes-前端代码审查报告.md`

**方法教训**：3 个后台 subagent 并行审查被环境 kill（TaskOutput 返回 killed）。
改为自己用 Grep 模式扫描 + 定向 Read 验证，效率反而更高、信噪比更好。
**下次遇到大仓库审查，直接走"正则扫描可疑模式 → 逐条 Read 验证"，别指望并行 subagent。**

**核心发现**：
- S1 `ConfigPage`:160-210,279-301 —— 全量覆盖式 `saveConfig`，初始化失败静默吞掉
- S2 `plugins/usePlugins.ts` —— `integrity` 在 `plugins/types.ts` 是**可选**字段，SRI 变成默认关闭；CSS 用 `<link>` 注入且完全无 SRI 机制
- M1 `App.tsx` SidebarTooltip —— render 期间 `getBoundingClientRect()` 读 DOM
- M2 `EnvPage`:609-624 —— loading 态永久卡死
- M7 `ICON_MAP` 硬编码 23 图标白名单，加页面必改 App.tsx
- 23 处空 catch；~50 处 timer（抽查 SessionsPage/ChannelsPage 清理正确）
- XSS 面干净：`dangerouslySetInnerHTML|innerHTML|outerHTML|insertAdjacentHTML` 全仓零命中
- **i18n M4 已实测更正**：en 714 / zh 635，**缺 79 个**（非之前估的 73）；`types.ts` 有 82 个 `?:` 可选字段故 `tsc` 不报错；
  被引用的 19 个缺失键**全部带 `??` 兜底**，中文界面**零空白**；真正风险是 i18n 无运行期回退层、全仓 556 处 `t.xxx` 仅 3.8% 有兜底
- **kanban 是死代码**：0 文件 / 0 引用，但 16 语言各带 ~150+ 条翻译，占 locale 文件 **~24%**
- **16 locale 全静态 import**（no lazy-load），首屏下载全部翻译
- 六个重型依赖（three/leva/gsap/motion/@observablehq/plot/@react-three/fiber）web/src 零直接引用
  → 实为 `@nous-research/ui` 的 **peerDependencies**（npm view 已核实）；UI 库还依赖 `sanitize-html`（正面：XSS 缓解存在）
- web 从 UI 库**内部子路径**导入（`@nous-research/ui/ui/components/*` 219 处）→ 脆弱耦合
- **无 lockfile** + `file:../apps/shared` 本地依赖 → 构建不可复现
- tsconfig `strict` 但缺 `noUncheckedIndexedAccess`；eslint 里维护者自曝 set-state-in-effect/ref-as-instance-var/manual-memo 反模式存在

**方法教训（重要）**：
- 第一轮回大仓库审查，派 3 个**后台** subagent → 被环境 `killed`。
- 第二轮回审查，派 3 个**并行前台** subagent（SendMessage 唤醒 paused）→ 全部 `429 频率限制`（17:37 重置），零产出。
- **结论**：并行 subagent 这条路在限流下不可靠。大仓库审查应直接由主 agent 做
  「解析脚本提取事实（i18n 键/依赖图）+ Grep 模式扫描 + 定向 Read 验证」，又快又准且不会丢结论。

  `saveConfig(config)` 全量写回，若 getConfig 响应漏键会静默抹掉服务端其他键（需后端 merge 佐证）
